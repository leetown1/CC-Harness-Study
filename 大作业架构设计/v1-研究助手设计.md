## 0. 为什么今天做这个（按 §0.5 讲透）

### 🧠 原理：为什么学架构不能"光读不练"？

> **知道 ≠ 懂**——你读了"95% Harness"——但没亲手**画过一次**模型和 Harness 的边界，**就永远停在"听过的概念"**。

学架构最有效的方式：
1. **读别人的**——今天看 CC 怎么做（`src/`）
2. **自己画一遍**——亲手把"模型"和"Harness"在白纸上分开
3. **在画的过程中暴露理解漏洞**——你以为自己懂了，画的时候才发现"原来我没想到权限"
4. **迭代**——v1 → v2 → v3，每次都补一个漏洞

**这是 Design Driven Learning**——比"读完写总结"深 10 倍。

### ⚙️ 实现：CC 怎么落地的？

- 📁 `src/query.ts` L307-1728 —— **1421 行** while(true) 循环
- 📁 `src/Tool.ts` L740-768 —— `TOOL_DEFAULTS` 工厂（Fail-Closed 默认值）
- 📁 `src/services/compact/autoCompact.ts` L66-73 —— **3 次熔断**

**真相**：CC 不是"一个 prompt + 一个 LLM"——**它是一个 1729 行的状态机**——里面**只有 50 行**真正在调 LLM。

### 🛣️ 路线：业界 3 种风格

| 风格 | 代表 | 特点 | 风险 |
|------|------|------|------|
| **极简** | 直接调 LLM API + 1-2 个工具 | Anthropic 推荐：能找到 simplest solution 就别做 agent | 复杂任务撑不住 |
| **轻量 Harness** | LangChain / 显式 Chain | 代码量 100-1000 行 | 灵活性差，**循环深度不可控** |
| **重型 Harness** | CC / Devin / Manus | 1000+ 行状态机，4 层压缩 + 5 层防御 | **过度工程**——新人做不出来 |

**你的 v1 选哪条路？**——**今天先做"极简 → 轻量"过渡**——**不要一上来就抄 CC 的 1729 行**。

## 1. 场景说明（v1 · 最简单版）

**你想做一个「研究助手 Agent」**——帮自己读 PDF 论文、总结成结构化笔记。

### 用户视角
1. 用户说：`帮我读 /Users/.../paper.pdf，总结成 200 字笔记，存到 notes/paper-summary.md`
2. Agent 读 PDF → 提取要点 → 写成 markdown → 存到指定路径
3. 用户看到 `paper-summary.md`，可以追问"第三部分再展开讲讲"

### 核心工具（最少 3 个）
- **`FileRead`**：读 PDF（或者用 PDF 解析库）
- **`FileWrite`**：写 markdown 笔记
- **`AskUserQuestion`**：问"摘要字数 200 还是 500？"

## 3. v1 你的答案（2026-06-17）

> 原文照抄

**Q1 · 模型 vs Harness 边界**
- 1a Harness（把文本丢给 LLM）
- 1b Harness（检查 PDF 是否存在）
- 1c LLM（让 LLM 总结）
- 1d Harness（检查文件覆盖）
- 1e Harness（解析 markdown 格式）

**Q2 · 循环步骤**
> 拿到第一步，必须得先请求 API，把用户请求发给 LLM，不然 harness 不是智能的，怎么知道用户那句话什么意思呢，然后根据返回的信息先检查本地有没有 PDF，找到 PDF。找到 PDF 后调用 fileread，提取文本。再把文本发给 LLM，LLM 分析。LLM 分析后返回。然后用 filewrite 写入。
>
> 要校验，要看看 LLM 返回要求调用的工具可以用，是安全的。
>
> 写文件失败，返回失败信息给 LLM，看看是不是工具用错了。
>
> 对结果不满意就继续调用。

**Q3 · 写文件权限**
- 要校验工具是否安全可用
- 写文件失败 → 回给 LLM 重试
- 不满意就继续调
- 只能写那个 markdown 文件，不能够去碰其他文件

**反问**：1a（构建请求）和 1c（让 LLM 总结）—— 都是"涉及 LLM"——**为什么一个归 Harness 一个归模型**？

### Q3 · 5 层防御里只用了 1 层

今天讲的 5 层纵深防御：

| # | 层级 | v1 用了？ | 备注 |
|---|------|---------|------|
| 1 | 静态规则 | ❌ | "禁止写 .env / .ssh / ~/.aws/credentials" |
| 2 | 路径保护 | ✅ | **你的"只能写那个 markdown 文件"** = 这一层 |
| 3 | 语义分析 | ❌ | "这 markdown 看起来合理吗" |
| 4 | 分类器 | ❌ | Auto-mode LLM 判断（v1 不用做） |
| 5 | 人工确认 | ❌ | 覆盖已有文件前弹窗问用户 |

**v1 用了 1 层（路径保护）—— 还差 4 层**。

**v1 缺的最关键 2 层**：
- ❌ **静态规则**——**不能写 .env、.ssh 密钥、其他用户的笔记**（v1 没考虑）
- ❌ **人工确认**——**覆盖已有文件前必须问用户**（v1 直接覆盖了）

**为什么这两层 v1 必须有**：
- 静态规则：用户**自己都没意识到**——他让你写 `paper-summary.md` —— **但 LLM 可能自作主张**写 `/etc/hosts`（路径保护挡不住，因为它在白名单里）——**静态规则兜底**
- 人工确认：v1 默认**直接覆盖**——**用户的旧笔记就没了**——**harness 永远不应该自作主张覆盖**

**Q2 · 重写循环 · LLM + Harness 协作**（15 分钟）

**v1 你写"先调 API 把用户请求发给 LLM"——**我之前误判为反模式——**我错了**——**完全正确**。

Harness **没有自然语言理解能力**——它拿到的是字符串，**不会自己解析**——**必须 LLM 提取参数**。

**真实 CC 模式**（调 LLM **多次** + Harness **360° 包裹**）：

```
1. 接收用户输入（自然语言字符串）
2. 【LLM-1】理解意图 + 提取参数（PDF 路径 / 字数 / 输出路径）  ← Harness 不会解析，必须调
3. Harness · 参数校验（路径合法？字数 1-10000？）
4. Harness · 文件存在检查（PDF 在不在？）
5. Harness · 路径白名单（输出路径必须在 notes/ 下）
6. Harness · 读 PDF（FileRead）
7. Harness · 上下文压缩（PDF 太长时裁剪）
8. 【LLM-2】理解 + 总结 PDF 内容                            ← 第二次调 LLM
9. Harness · 输出校验（markdown 格式？长度合理？）
10. Harness · 写文件（FileWrite）
11. Harness · 错误处理（写失败 → 回给 LLM-3 → 重试）
12. 【LLM-3】反思 / 用户反馈（用户不满意 → 回到第 8 步）
```

**关键洞察**：
- 循环里**调 LLM 不止 1 次**（v1 你没说错——是 LLM-1 → LLM-2 → LLM-3 多次）
- **每次调 LLM 前后都被 Harness 工程包裹**——**这才是 95% Harness 的真正含义**
- **不是 "16 步里只有 1 步调 LLM"**——是 "**调 LLM 是主决策点**——**但每次调 LLM 周围 90% 都是 Harness**"

**v2 你的任务**：
- **至少 12 步**循环
- **每步标出来**："🤖 LLM"（调 LLM）/ "⚙️ Harness"（工程活）
- **至少 2 次调 LLM**
